## 7. Known limits

1. The fake backend's layout check fails on its stale calibration; `enforced: false`; the live check decides.
2. Job order: the runner submits the grid-point jobs before the null-control jobs (Section 1); the null floor is measured on the same day,
   in the same Batch, not before the grid points.
3. Whole-list refusal: a live cut failure on any of the 85 qubits refuses the combined list, including the n = 20 grid. Fallback: the two
   source lists.
4. The n = 20 Gate 1 predictions are the 19 Sep placement's (edge 93_103, no broken coupler); the main-grid rows on the (8, 2) / 94_104 / 95-96
   placement are not yet re-drawn (`redraw_gate1b.py --main-grid`, about 130 core-minutes). The anchor selection for (a) is insensitive to
   this (L = 8 at 2.2e-4 against a floor of 2e-6 or 9e-5; L = 12 at 5e-6).
5. `gradvar.analysis.gates.null_floor_for` takes the **first** measured `null_control` row at (n = 20, 4096 shots) without filtering on L or
   level; on day 1 four such rows exist (L = 0 at levels 0 and 1, L = 1 at levels 0 and 1) and they differ by a factor of about 45. The post-run
   review must select `null_L0_n20_r0` explicitly (or the evaluator gains an `L == 0 and resilience_level == 0` filter before it runs). Follow-up
   for the analysis pipeline, not a list change.
6. Q114 (cone qubit, neighbour of observable qubit 104) read T1 = 3.7 us, T2 = 6.4 us in the 13:44Z calibration (80 / 122 us at 03:08Z). T1 / T2
   are not Deviation 26 cuts, so neither the generator nor the live check moves the patch on it. The L = 8 and 12 circuits last 5.7-8.5 us
   before readout, so a 3.7 us T1 on a cone qubit is a fully decohered neighbour of the observable. If the 21 Sep snapshot still shows it, the
   reviewer decides before posting: run as placed and log it (Section 2 allows a one-column shift only under the cut rules), or record a
   deviation adding a coherence floor to the placement rule. Not decided here.
7. Q47 (n60 / n80 / n100 patches) has no `init_error` entry in the raw properties; Deviation 22 (ii) cannot be applied to it (readout cut applies).
8. The lists' `campaign.pre_registration` string reads "v0.12.0"; the pre-registration is at v0.13.1 (Deviations 50 and 51 change no point,
   seed or budget). Bump the string with the run-day regeneration (`PREREG` in the generator) so the arming commit names the version in force.

## 9. What happens if Gate 2 fails

Under Section 5's pause rule the campaign pauses: day 2 (the remaining main grid, about 43.9 min at 1 us: grid_n40 / n60 / n80 / n100 /
n100_16384 / n40_repeat) and day 3 (the dial arm) are not armed until the cause is logged and the PI signs a recorded deviation (Section 8 of
the pre-registration). Spent by then: day 1's about 6 Flex minutes (1.6 from the 2.6-minute null-control reserve item, 4.4 from the
190.5-minute main-grid line; about 8 at the smoke test's charge ratio), out of 359.13 remaining; the data are not lost — the null floors and
the n = 20 rung are pre-registered points of the main grid whatever Gate 2 says. What a failure means by clause: (a) the n = 20 depth-8
variance is not resolved above the measured null floor at M = 200, so the depth fall H2 and the n-scaling H1 cannot be read on hardware as
designed — the remedies are the PI's (a deviation choosing a shallower confirmatory anchor or more shots per point, funded from the 4.9
unallocated reserve minutes and the surplus rule), or the hardware stage ends and the result is a simulation-only note (Section 3b's stop-rule
outcome by analogy; Gate 1 passed, so the simulation record stands); (b) or (d) the recomputed or measured grid does not fit the 190.5-minute
line at the granted rep_delay — the Section 6 cut order applies before day 2 is booked (M stays 200; L = 12 rows first); (e) a readout excursion
(two or more cone qubits above 1.5x, or any qubit above the cut) — re-read at the next calibration and re-post the pre-flight for day 2; the
day-1 data are kept with the excursion logged in the Deviations table. Kill (c) / (d) are not touched by day 1. No minutes are spent on a
paused campaign; the reserve is not drawn without a recorded decision.

## 10. Retrieval and the human steps

**Ids file the runner writes** (`gradvar.hardware.execute_joblist` -> `write_ids_file(ids_file_path(run_root, <UTC date>, jl["name"]))`),
right after the last submission and before any result is awaited:

```
data/runs/<YYYY-MM-DD, UTC date of submission>/paper1_day1_null_grid_n20_job_ids.json
```

The Action commits it even if the run is later killed (`if: always()`). The retrieve workflow is Actions -> "retrieve hardware jobs" -> Run
workflow -> input **`ids_file`** = that path (it must be a committed file under `data/runs/`); it collects the 14 jobs into the same bundles
and CSV rows as the live path, waits for queued jobs (350-minute limit), commits, and submits nothing. The submitting run should be dispatched
with **`submit_only` ticked** so it returns after writing the ids file (the 20 Sep queue was 6 h 28 min; the 6-hour Action limit killed the
run that waited).

### Human steps (Owais), verbatim

**Step 1 — arm (after this pre-flight is posted in the thread and its permalink copied).** In `data/joblists/paper1/day1_null_grid_n20.json`
